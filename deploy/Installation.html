Quizzer auf dem eigenen Rechner

Docker Desktop trägt Datenbank, REST-API und Mediendateien — das WPF meldet sich dort an.

Stand 23.10.2026 (Meldungen M24–M29). Jeder Schritt ist an diesem Tag auf dem Entwicklungsrechner durchgespielt worden; was nicht gemessen ist, steht unter Was gemessen ist und was nicht.

Am Ende läuft: ein Stapel aus vier Containern unter Docker Desktop, erreichbar nur auf diesem Rechner unter https://localhost:8543. Spiele, Fragen, Mitspieler, Ergebnisse und Designs liegen im Container, ebenso alle Bilder und Töne. Das WPF arbeitet mit einem Konto dagegen.

Verwandte Dateien: deploy/README.md (Betrieb, Sicherung, Tailscale) und deploy/.env.example (Vorlage der Umgebungsdatei).

Der Aufbau auf einen Blick

Wie das WPF mit dem Docker arbeitet: Beim Anmelden holt es alles, was das Konto sehen darf, in eine eigene lokale Zwischendatenbank (Quizzer_Server_ plus 12 Zeichen der Konto-Kennung, auf derselben LocalDB) und die Medien in den Datenordner C:\ProgramData\Quizzer\Daten — denselben, den auch der Einzelbetrieb benutzt (Meldung M28: „ein Ordner für alles“). Danach laufen alle Masken unverändert lokal; jedes Speichern geht drei Sekunden später zum Server. Fällt die Verbindung weg, wird lokal weitergespielt und später nachgeschickt. Angemeldet wird bei jedem Start (Kennwort eingeben); „Abmelden“ im Hauptfenster führt zurück ins Anmeldefenster, und „Daten von diesem Rechner entfernen“ in den Einstellungen räumt alles auf einmal weg.

Umgebungsvariablen — was wohin gehört

Stand 23.10.2026. Hier steht jede Variable des Stapels und der Skripte — aus deploy/.env.example, aus den environment:-Blöcken von deploy/docker-compose.yml, aus dem Dockerfile und aus jedem GetEnvironmentVariable im Repo (am 23.10.2026 durchsucht; am laufenden Stapel mit docker inspect gegengeprüft). Dazu die Dateien, in denen das WPF seine Einstellungen hält — das WPF selbst liest keine Umgebungsvariable.

Eine Einstellung des Stapels durchläuft drei Stationen, und an jeder kann sie anders heißen: der Betreiber trägt einen Wert in deploy/.env ein, docker-compose.yml reicht ihn unter einem zweiten Namen an einen Dienst weiter, und das Programm im Container liest ihn beim Start.

.env                 QUIZZER_APP_PASSWORD=HIER-EIN-ZUFAELLIGES-KENNWORT
docker-compose.yml   migrator:  Quizzer__AppLogin__Password: ${QUIZZER_APP_PASSWORD}
                     api:       ConnectionStrings__Quizzer: "Server=sql;...;Password=${QUIZZER_APP_PASSWORD};..."
Wirkung              der Migrator legt damit die Anmeldung quizzer_app an (oder setzt ihr Kennwort neu),
                     die API meldet sich damit bei jedem Start am SQL Server an

Der doppelte Unterstrich trennt die Ebenen: Quizzer__Jwt__SigningKey ist der Eintrag SigningKey im Abschnitt Quizzer:Jwt. Der Server hat keine appsettings.json (im Abbild nachgesehen) — die Umgebung ist seine einzige Quelle.

Ein Neustart übernimmt keine Umgebungswerte.

Nach jeder Änderung an .env den Stapel mit docker compose up -d neu anlegen lassen — er legt jeden Dienst neu an, dessen Werte sich geändert haben. Ein docker restart startet den alten Container mit den alten Werten, und nichts meldet es.

Das sa-Kennwort später zu ändern ist kein Eintrag in der .env.

SQL Server übernimmt MSSQL_SA_PASSWORD laut Microsoft nur beim ersten Start mit leerem Volume — hier nicht nachgemessen. Danach stimmten .env und Datenbank nicht mehr überein, und der Migrator scheiterte. Wer es ändern will: erst in SQL Server (ALTER LOGIN sa WITH PASSWORD = …), dann in der .env, dann docker compose up -d.

Der Aufbau, Schritt für Schritt

Alle Befehle in einer PowerShell-7-Konsole (pwsh), ab Schritt 3 im Ordner deploy des Repos.

1

Das Repo holen

git clone https://github.com/Heumayr/Quizzer.git
cd Quizzer

Die Harness-Submodule braucht der Stapel nicht.

2

PowerShell 7, falls sie fehlt

winget install --id Microsoft.PowerShell --source winget --exact

Danach eine neue Konsole mit pwsh öffnen.

3

Die Umgebungsdatei erzeugen

cd deploy
.\new-secrets.ps1

Legt .env mit Zufallswerten an; eine bestehende überschreibt es nie. Dann den Port prüfen:

netstat -ano | findstr ":8443 "

Steht dort eine Zeile mit LISTENING, ist er belegt — in der .env einen freien eintragen, etwa QUIZZER_PORT=8543.

4

Das Zertifikat

.\zertifikat-lokal.ps1

Legt certs\server.crt, certs\server.key (nur für den eigenen Benutzer lesbar) und certs\server.sha256 an — ECDSA P-256, gültig für localhost, den Rechnernamen und 127.0.0.1, fünf Jahre. Die Ausgabe nennt den Fingerabdruck. Ein vorhandenes Zertifikat bleibt; ersetzen nur mit -Neu (dann ändert sich der Fingerabdruck im WPF).

5

Den Stapel starten

docker compose up -d --build
docker compose ps -a

Beim ersten Mal lädt Docker SQL Server (1,7 GB) und baut das Server-Abbild — einige Minuten. Erwartet:

api       running   Up …
caddy     running   Up …
migrator  exited    Exited (0) …
sql       running   Up … (healthy)

Kurzprobe der Tür (der Pfad ist /api/v1/version, /version antwortet 401):

curl.exe --cacert certs\server.crt https://localhost:8543/api/v1/version
{"apiVersion":1,"syncFormatVersion":1,"serverVersion":"1.0.0"}
6

Den bisherigen Bestand übernehmen

.\bestand-uebernehmen.ps1

Spielt die LocalDB des Einzelbetriebs (aus Quizzer.DataModels/appsettings.json, überschrieben von settings.json) samt Datenordner in den Stapel: Datenbank zurückspielen, Medien in quizzer-media, Migrator, dann das Design „Hausdesign“ aus den 12 Grundtexturen des Datenordners — es wird jedem Spiel ohne Design zugewiesen. Der Grund: der Abgleich lädt Texturen, die direkt im Datenordner liegen, nie hoch; als Design reisen sie mit dem Spiel zu jedem Rechner. Das WPF auf den Docker umstellen

.\wpf-verbinden.ps1

Setzt in %APPDATA%\Quizzer\settings.json den Servermodus, https://localhost:<QUIZZER_PORT> und den Fingerabdruck; alles andere in der Datei bleibt, die alte Fassung liegt als settings.json.vor-wpf-verbinden-<Zeit> daneben. Von Hand geht dasselbe im WPF unter Einstellungen: „Mit Konto am Quizzer-Server arbeiten“, die Adresse, „Fingerabdruck des Zertifikats (nur bei einem selbst erzeugten)“ aus certs\server.sha256, dann „Server prüfen“.

Angemeldet wird bei jedem Start (Meldung M28, „immer fragen“): der Name ist vorbelegt, der Cursor steht im Kennwortfeld. Ist der Server nicht erreichbar, steht sofort „Ohne Server mit dem letzten Stand weiterarbeiten“ da. „Abmelden“ im Hauptfenster (Abschnitt „Spielleitung“) schickt Offenes, meldet am Server ab und startet neu ins Anmeldefenster — dort geht auch ein anderes Konto. Danach, in dieser Reihenfolge:

  • Kennwort ändern (Hauptfenster) — der Wert in der .env ist danach nur noch ein alter.
  • Konten verwalten: ein eigenes Konto anlegen und dabei den eigenen Mitspieler wählen (bestehende Mitspieler ohne Konto stehen zur Auswahl). Dann gehören dessen Spiele dem eigenen Konto; das Admin-Konto hat einen eigenen, neuen Mitspieler und sieht als Admin trotzdem alles.
  • Für die Freunde ebenso: je ein Konto, an ihren Mitspieler gehängt.

Das Anmeldefenster nicht einfach schließen.

Wer es schließt, bekommt keine Meldung, sondern ein Programm, das sich wortlos beendet — von außen nicht von einem Absturz zu unterscheiden.

Die Sicherung einplanen

In der .env QUIZZER_BACKUP_COPY_TO auf ein zweites Laufwerk setzen, dann:

.\backup.ps1                 # einmal von Hand: backups\<Zeitstempel>\quizzer.bak + medien.tar.gz
.\aufgaben-einrichten.ps1    # Sicherung täglich 03:12, Zertifikat sonntags 04:17

Die Aufgaben laufen nur, solange der Benutzer angemeldet ist (Sperren genügt), weil Docker Desktop in der Benutzersitzung läuft. Die Sicherungen sind nicht verschlüsselt. Die Zertifikatsaufgabe ist für Tailscale gedacht; mit dem lokalen Zertifikat endet sie mit Fehler, weil QUIZZER_TS_HOSTNAME leer ist — das stört die Sicherung nicht.

Später: Laptop und Freunde

Von einem anderen Gerät ist 127.0.0.1 nicht erreichbar. Der vorgesehene Weg ist Tailscale (Entscheidung F20): Tailscale auf diesem Rechner, QUIZZER_BIND_ADDRESS auf die Tailscale-Adresse (tailscale ip -4), QUIZZER_TS_HOSTNAME setzen und das Zertifikat mit .\zertifikat-erneuern.ps1 holen statt mit zertifikat-lokal.ps1. Ein tailscale cert-Zertifikat ist öffentlich vertrauenswürdig — dann braucht kein WPF einen Fingerabdruck, und alle tragen https://<rechner>.<tailnet>.ts.net:<QUIZZER_PORT> ein, auch dieser Rechner. Ablauf: deploy/README.md, Abschnitt „Einrichten“.

Was gemessen ist und was nicht

Am 23.10.2026 auf dem Entwicklungsrechner gemessen

  • docker compose up -d --build grün; Tür nur auf 127.0.0.1:8543; HSTS, nosniff, no-referrer in der Antwort; ohne Fingerabdruck abgewiesen.
  • Fingerabdruck aus zertifikat-lokal.ps1 mit OpenSSL gegengerechnet — gleich.
  • bestand-uebernehmen.ps1 mit der Ausgabe oben; zweiter Lauf ohne -Ersetzen bricht ab, die API bleibt unberührt.
  • Mit dem Client des WPF (Quizzer.Client) gegen den Stapel: Anmeldung, Abholen in eine Wegwerf-Zwischendatenbank — 211 Zeilen, 33 Mediendateien, keine Probleme; alle drei Spiele auf Hausdesign; die Texturen byteweise gleich mit dem Datenordner; ein falscher Fingerabdruck abgewiesen.
  • settings.json aus wpf-verbinden.ps1 von UserSettings.Load() so gelesen.
  • backup.ps1 gegen den Stapel: quizzer.bak 6,5 MB, medien.tar.gz 75 MB.
  • Das WPF aus dem Debug-Build gestartet (wie Visual Studio), per UI Automation: Anmeldefenster verlangt das Kennwort (kein Selbst-Anmelden, Cursor im Kennwortfeld); die Anmeldung holt nach C:\ProgramData\Quizzer\Daten (42 → 54 Dateien, Hausdesign dazu); „Abmelden“ fragt im neuen Meldungsfenster, „Nein“ lässt angemeldet, „Ja“ beendet, löscht den gemerkten Ausweis und startet neu ins Anmeldefenster.

  • restore.ps1 und aufgaben-einrichten.ps1 auf diesem Rechner.
  • Ein Neustart des Rechners mit laufendem Stapel.
